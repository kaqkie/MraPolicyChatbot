# MRA Internal Policy Chatbot

## Project Overview

MRA Internal Policy Chatbot is an internal web application for MRA employees.
Once complete, employees will log in with a simple username and password and
ask questions about approved MRA policy documents only.

This repository is being built **phase by phase**. Each phase adds a specific,
scoped piece of functionality; no phase implements features from a later
phase ahead of schedule. See [`docs/PROJECT_PLAN.md`](docs/PROJECT_PLAN.md)
for the full roadmap, and [`CLAUDE.md`](CLAUDE.md) for the standing project
rules and constraints that apply throughout development.

**Current phase: Phase 6 — Local AI Chat (Ollama integration).**
The Chat page is now a real, working chatbot: questions are embedded and
matched against policy chunk embeddings (generated locally via
[Ollama](https://ollama.com) during Phase 5's processing pipeline, no cloud
AI), and answers are generated by a local LLM grounded strictly in the
matched policy excerpts, with source policy titles shown under each answer.
If no policy content matches closely enough, or if Ollama isn't running,
the chatbot says so plainly rather than guessing. The same chatbot is also
reachable by voice (speech in, the identical answer pipeline, spoken answer
out), and scanned/image-only policy PDFs are handled via a local OCR
fallback (see [Scanned/image-only PDFs](#scannedimage-only-pdfs-ocr)
below). See [Testing the Chatbot](#testing-the-chatbot-phase-6) below to
set this up locally. No query logging, feedback, or usage analytics yet —
that's Phase 7. (Admin **Settings**, letting an admin change the AI
connection, matching threshold, department list, and their own password at
runtime, was added ahead of Phase 7 as a refinement of the existing Admin
area — see [Admin Settings](#admin-settings).)

## Technology Stack

- **Language:** C#
- **Framework:** ASP.NET Core MVC (.NET 8 LTS)
- **Views:** Razor Views
- **UI:** Bootstrap 5 (via CDN)
- **Database:** SQL Server, accessed with [Dapper](https://github.com/DapperLib/Dapper) (no Entity Framework)
- **Tooling:** Local/free tooling only — no paid or cloud services

## Running the Application Locally

From the repository root:

```bash
dotnet restore
dotnet build
dotnet run --project src/MraPolicyChatbot
```

By default the app will bind to a local Kestrel URL such as
`http://localhost:5000` (the exact port is printed in the console output when
the app starts, and is also configurable in
`src/MraPolicyChatbot/Properties/launchSettings.json`).

> **Since Phase 3: you must run over HTTPS to log in.** The session cookie
> is marked `Secure`, so a real browser will silently refuse to send it back
> over plain `http://` — login will look like it redirects successfully but
> you'll immediately be bounced back to the Login page. Use the `https`
> launch profile instead:
> ```bash
> dotnet run --project src/MraPolicyChatbot --launch-profile https
> ```
> This binds to `https://localhost:7184` (see `launchSettings.json`). The
> first time, your OS/browser may need to trust the ASP.NET Core
> development certificate — if prompted, run `dotnet dev-certs https --trust`.

To run with file-watching / auto-rebuild during development:

```bash
dotnet watch --project src/MraPolicyChatbot run --launch-profile https
```

## Database Setup

Phase 2 introduces a SQL Server database. The application will not run
correctly until this is set up, because `Program.cs` now registers data
access services that expect a valid connection string.

### 1. Install SQL Server

Pick whichever fits your machine — all are free:

- **Windows:** install
  [SQL Server Express](https://www.microsoft.com/en-us/sql-server/sql-server-downloads)
  (or Developer edition, also free, if you already have a license-eligible
  use case). During setup, "Basic" install type is enough for local
  development. Also install
  [SQL Server Management Studio (SSMS)](https://learn.microsoft.com/en-us/sql/ssms/download-sql-server-management-studio-ssms)
  if you'd like a GUI for browsing the database.
- **macOS/Linux:** run SQL Server in a container via Docker:
  ```bash
  docker run -e "ACCEPT_EULA=Y" -e "MSSQL_SA_PASSWORD=YourStrong!Passw0rd" \
    -p 1433:1433 --name mra-sql -d mcr.microsoft.com/mssql/server:2022-latest
  ```
  (If you use this route, the app's `Trusted_Connection=True` connection
  string won't work as-is — see the note at the end of this section.)

### 2. Run the setup script

The schema and seed data live in
[`docs/database-setup.sql`](docs/database-setup.sql). It is safe to re-run —
every statement checks whether it's already applied first.

Using `sqlcmd` (installed alongside SQL Server, or as the
[standalone `sqlcmd` utility](https://learn.microsoft.com/en-us/sql/tools/sqlcmd/sqlcmd-utility)):

```bash
sqlcmd -S localhost -E -i docs/database-setup.sql
```

(`-E` uses your current Windows login via integrated/trusted authentication,
matching the app's default connection string. Add `-U sa -P <password>` instead
of `-E` if you're using SQL authentication, e.g. with the Docker container above.)

Or open `docs/database-setup.sql` in SQL Server Management Studio / Azure
Data Studio, connect to your local server, and execute it.

### 3. Verify the database was created

Any of the following confirm success:

```sql
-- In sqlcmd, SSMS, or Azure Data Studio:
SELECT name FROM sys.databases WHERE name = 'MraPolicyChatbot';
USE MraPolicyChatbot;
SELECT Username, Role FROM Users;   -- should show 'admin' and 'employee'
```

### Test accounts (local/dev only)

Seeded by `docs/database-setup.sql`, passwords hashed with bcrypt (cost 10):

| Username | Password | Role |
|----------|----------|------|
| `admin` | `admin123` | Admin |
| `employee` | `employee123` | Employee |

These are throwaway local development credentials, not real secrets — do
not reuse them anywhere else.

### Connection string

The connection string lives in `src/MraPolicyChatbot/appsettings.json`:

```json
"ConnectionStrings": {
   "DefaultConnection": "Server=localhost\\SQLEXPRESS;Database=MraPolicyChatbot;Trusted_Connection=True;TrustServerCertificate=True;"
}
```

`Trusted_Connection=True` uses your Windows login (integrated security) and
is the default for a local SQL Server Express/Developer install. If you're
instead running SQL Server via Docker (SQL authentication only), change it
to something like:

```
Server=localhost;Database=MraPolicyChatbot;User Id=sa;Password=YourStrong!Passw0rd;TrustServerCertificate=True;
```

For local development, prefer `appsettings.Development.json` to override
this rather than committing real credentials to `appsettings.json`.

## Testing Text Extraction & Chunking (Phase 5)

1. Log in as `admin`, go to **Admin Dashboard → Upload New Policy**, and
   upload a real PDF or DOCX file (Title/Category can be anything).
2. You'll land back on the policy list. The new row's Status column starts
   as "⏳ Processing..." — processing runs in the background, so refresh
   the page after a few seconds.
3. Once done, Status should flip to "✓ Processed" and the Chunks column
   will show a count like "12 chunks". If extraction couldn't get any text
   out of the file (e.g. a corrupt file, or a scan OCR couldn't read),
   Status shows "✗ Failed" instead — hover it to see the specific error
   message.
4. To retry processing the *same* stored file (e.g. after fixing an Ollama
   connection problem, or just to regenerate embeddings), click **Retry
   processing** on any row — it clears and regenerates that policy's
   chunks without needing to touch the file itself.
5. If the actual document content has changed — a new revision of the
   policy — use **Edit** on that row instead: the Edit Policy screen has an
   optional "Replace file" field. Uploading a file there swaps the stored
   file and automatically re-extracts text and rebuilds chunks/embeddings
   in the background, the same as a fresh upload. Editing just the
   Title/Department without choosing a replacement file leaves the
   existing chunks alone.

### Scanned/image-only PDFs (OCR)

A PDF that's actually a scan (a signed circular, for instance) has no
selectable text layer for PdfPig to read — that's a real limitation of the
file, not a bug. For exactly those pages, extraction automatically falls
back to [Tesseract](https://github.com/tesseract-ocr/tesseract) OCR, which
runs fully locally (no cloud/paid API). This needs the English language
data file already included in this project at
`src/MraPolicyChatbot/App_Data/tessdata/eng.traineddata` — nothing to
install or download separately; the `Tesseract` NuGet package (see
`MraPolicyChatbot.csproj`) bundles its own native engine binaries for
Windows. A PDF with a normal text layer never touches OCR at all and
processes exactly as before.

### Verify chunks in the database

```sql
USE MraPolicyChatbot;

-- Processing status + chunk count per policy:
SELECT p.Id, p.Title, p.IsProcessed, p.ProcessingError, COUNT(c.Id) AS ChunkCount
FROM dbo.Policies p
LEFT JOIN dbo.PolicyChunks c ON c.PolicyId = p.Id
GROUP BY p.Id, p.Title, p.IsProcessed, p.ProcessingError
ORDER BY p.Id;

-- The actual chunks for one policy, in order (replace 1 with a real Id):
SELECT ChunkOrder, LEFT(ChunkText, 100) AS ChunkPreview, LEN(ChunkText) AS ChunkLength
FROM dbo.PolicyChunks
WHERE PolicyId = 1
ORDER BY ChunkOrder;
```

## Testing the Chatbot (Phase 6)

The chatbot answers are generated entirely by a **local** [Ollama](https://ollama.com)
server — no cloud AI API, no external service. You need Ollama installed
and running before the chat page will produce real answers.

### 1. Install Ollama and pull the two models

Install Ollama for your OS from [ollama.com/download](https://ollama.com/download),
then pull the embedding model and the chat model used by default (both
configurable — see below):

```bash
ollama pull nomic-embed-text
ollama pull llama3.1
```

Ollama runs as a local background service listening on
`http://localhost:11434` by default — no separate "start" step is normally
needed once it's installed, but you can confirm it's up with:

```bash
curl http://localhost:11434
```

which should respond with `Ollama is running`.

### 2. Configure the models/URL (optional)

`appsettings.json`'s `"Ollama"` section only supplies the *initial*
defaults (used to seed the database — see `docs/database-setup.sql`):

```json
"Ollama": {
  "BaseUrl": "http://localhost:11434",
  "EmbeddingModel": "nomic-embed-text",
  "ChatModel": "llama3.1"
}
```

Day to day, change these from the app itself instead: log in as `admin`
and go to **Admin Dashboard → Settings**. That page also controls the
answer-matching sensitivity threshold and the department list, and takes
effect immediately — no restart needed. See
[Admin Settings](#admin-settings) below.

### 3. Backfill embeddings for already-uploaded policies

Embeddings are generated as part of the Phase 5 processing pipeline. If you
uploaded policies **before** installing Ollama, their chunks won't have
embeddings yet. Fix this by clicking **Retry processing** on those rows in
the Admin Dashboard (this regenerates chunks and embeddings from scratch) —
Ollama must be running when you do this.

### 4. Ask a question

1. Log in as `admin` or `employee` and go to the **Chat** page.
2. Type a question that's actually covered by one of your uploaded
   policies (e.g. "How many days of annual leave am I entitled to?" if a
   leave policy is uploaded and processed) and press **Send**.
3. You should get a real, generated answer with a "Source: ..." line
   naming the policy it came from.
4. Ask something unrelated to any uploaded policy (e.g. "What's the
   weather today?") — you should get the fixed "I don't have information
   about that in the approved policy documents" response, not a guess.
5. To test the "Ollama unavailable" path, stop the Ollama service and ask
   a question — you should see "The chatbot is temporarily unavailable..."
   rather than an error page.
6. To test voice mode, click the circular voice button next to the
   composer — it greets you, listens for a spoken question through your
   browser's microphone, and answers using the exact same chatbot behind
   the scenes (same processed policies, same matching, same fallback
   messages), just spoken aloud instead of typed. A real answer from a
   local LLM can take a while, especially the first question after Ollama
   loads the model into memory — voice mode says "Still thinking..." if
   it's taking longer than a few seconds, rather than going silent.

## Admin Settings

Log in as `admin` and open **Admin Dashboard → Settings** to change, at
runtime, without editing any file:

- The Ollama address and the two model names (embedding + answer)
- The answer-matching sensitivity threshold (0–1; higher is stricter about
  what counts as a real match before falling back to "I don't have that
  information")
- The department list shown on Upload Policy / Edit Policy — add a line for
  a new department, delete a line to remove one, or edit the text to rename
  one; a "Manage departments" link on Upload Policy, Edit Policy, and the
  Policy Management list jumps straight here
- Your own admin password

These are stored in the database (`dbo.AppSettings`, added by
`docs/database-setup.sql`), so if you're updating an existing database
rather than starting fresh, re-run that script first — it's safe to re-run
and will only add the new table/seed rows, leaving your existing users and
policies untouched.

### Verify embeddings in the database

```sql
USE MraPolicyChatbot;

-- Chunks with vs. without an embedding, per policy:
SELECT p.Id, p.Title,
       COUNT(c.Id) AS ChunkCount,
       SUM(CASE WHEN c.Embedding IS NOT NULL THEN 1 ELSE 0 END) AS ChunksWithEmbedding
FROM dbo.Policies p
LEFT JOIN dbo.PolicyChunks c ON c.PolicyId = p.Id
GROUP BY p.Id, p.Title
ORDER BY p.Id;
```
